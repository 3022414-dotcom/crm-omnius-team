# Feature Specification: F-01 Схема данных и миграции

**Created**: 2026-05-24

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Развёртывание системы с нуля (Priority: P1)

Новый участник команды или сервер получает чистую базу данных. Разработчик запускает одну команду — и вся структура данных для CRM создаётся автоматически: все сущности (пользователи, компании, контакты, сделки, заметки, вложения, активности), связи между ними, правила автоматического обновления временных меток и поисковые индексы.

**Why this priority**: Без этого шага невозможно запустить ни одну другую функцию CRM. Это фундамент всей системы.

**Independent Test**: Можно протестировать, запустив команду развёртывания на чистой базе и проверив, что все сущности созданы и доступны для записи.

**Acceptance Scenarios**:

1. **Given** чистая база данных без таблиц, **When** выполняется команда развёртывания схемы, **Then** в базе появляются все необходимые таблицы, индексы и правила — система готова к работе
2. **Given** схема уже развёрнута, **When** команда развёртывания запускается повторно, **Then** команда завершается успешно, существующие данные не изменяются
3. **Given** схема развёрнута и заполнена данными, **When** выполняется команда отката, **Then** все таблицы удаляются без ошибок

---

### User Story 2 — Начальные учётные записи команды (Priority: P2)

После создания схемы в систему автоматически добавляются учётные записи четырёх участников команды omnius.team с корректными ролями. Никакой ручной настройки не требуется.

**Why this priority**: Система авторизации (F-02) напрямую зависит от наличия записей участников команды. Без этого шага никто не сможет войти в CRM.

**Independent Test**: После выполнения начального заполнения данными можно проверить, что все четыре участника присутствуют с правильными ролями.

**Acceptance Scenarios**:

1. **Given** схема создана, **When** выполняется команда начального заполнения данными, **Then** в системе появляются 4 участника: 2 с ролью «администратор» (Дмитрий Твердохлебов, Юлия Шевцова), 1 с ролью «менеджер» (Анастасия Стефанова), 1 с ролью «наблюдатель» (Илья Болховский)
2. **Given** начальное заполнение уже выполнено, **When** команда заполнения запускается повторно, **Then** дублирующихся записей не создаётся

---

### User Story 3 — Эволюция схемы со временем (Priority: P3)

Когда в будущем потребуется изменить структуру данных (добавить поле, таблицу, индекс), это делается через версионированные файлы изменений. История всех изменений схемы отслеживается и воспроизводима.

**Why this priority**: Без версионирования изменений невозможно безопасно вносить правки в схему на работающей системе.

**Independent Test**: Можно протестировать, создав новый файл изменения и убедившись, что система применяет только новые изменения, не затрагивая уже применённые.

**Acceptance Scenarios**:

1. **Given** схема версии N развёрнута, **When** добавляется новый файл изменения и запускается команда обновления, **Then** применяется только новое изменение, существующие данные сохранены
2. **Given** изменение применено, **When** запрашивается статус миграций, **Then** система показывает, какие изменения применены и какие ожидают применения

---

### Edge Cases

- Что происходит при запуске команды развёртывания без подключения к базе данных? → Ошибка с понятным сообщением, никаких частичных изменений
- Что если команда развёртывания прерывается на середине? → Транзакция откатывается, база остаётся в исходном состоянии
- Что если в начальных данных указан email участника, который уже существует в базе? → Дублирование не допускается, команда завершается без ошибок

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА предоставлять единую команду для создания полной структуры данных с нуля
- **FR-002**: Система ДОЛЖНА создавать все сущности CRM: пользователи, компании, контакты, сделки, связи «сделка–контакт», заметки, вложения, активности, сессии
- **FR-003**: Система ДОЛЖНА автоматически обновлять отметку времени последнего изменения при каждом обновлении записи — без участия кода приложения
- **FR-004**: Система ДОЛЖНА поддерживать роли пользователей как фиксированный список допустимых значений на уровне хранилища данных: `admin`, `bdm`, `viewer`
- **FR-005**: Система ДОЛЖНА обеспечивать ссылочную целостность со следующим поведением при удалении: удаление Аккаунта устанавливает NULL в account_id у связанных Контактов и Сделок (записи сохраняются); удаление Аккаунта, Контакта или Сделки каскадно удаляет связанные Заметки, Вложения, Активности
- **FR-006**: Система ДОЛЖНА обеспечивать быстрый поиск по ключевым полям: наименование компании, имя/фамилия/email контакта; email контакта не является уникальным — несколько контактов могут иметь одинаковый адрес
- **FR-007**: Система ДОЛЖНА поддерживать единицы «заметок», «вложений» и «активностей», привязанных к любой из трёх сущностей: компания, контакт или сделка
- **FR-008**: Система ДОЛЖНА предоставлять возможность отката структуры данных к предыдущему состоянию
- **FR-009**: Система ДОЛЖНА при первоначальном заполнении добавлять четырёх участников команды с корректными ролями, не создавая дублей при повторном запуске
- **FR-010**: Сущность «Контакт» ДОЛЖНА поддерживать необязательное поле ссылки на фото профиля — один файл на контакт; это поле не является вложением и хранится отдельно от таблицы вложений

### Key Entities

- **Пользователь (User)**: участник команды omnius.team, имеет роль (admin/bdm/viewer), идентифицируется по email, связан с Google-аккаунтом
- **Компания (Account)**: организация — клиент или потенциальный клиент, имеет владельца из команды
- **Контакт (Contact)**: физическое лицо, связано с компанией (необязательно), может иметь фото, имеет владельца из команды
- **Сделка (Deal)**: коммерческое предложение/переговоры, имеет этап воронки, связана с компанией (необязательно — account_id NULL как при создании, так и при удалении компании), может быть связана с несколькими контактами
- **Заметка (Note)**: текстовая запись, привязана к компании, контакту или сделке — но не к нескольким одновременно
- **Вложение (Attachment)**: файл, привязан к компании, контакту или сделке
- **Активность (Activity)**: задача или событие (звонок, встреча, письмо, задача), привязана к компании, контакту или сделке
- **Сессия (Session)**: пользовательский сеанс для сохранения авторизации между запросами

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Полная структура данных CRM создаётся с нуля менее чем за 60 секунд на стандартном оборудовании
- **SC-002**: Повторный запуск команды развёртывания не приводит к ошибкам и не изменяет существующие данные (100% идемпотентность)
- **SC-003**: После развёртывания все четыре участника команды могут быть найдены в системе с корректными ролями (4 из 4)
- **SC-004**: Поиск по наименованию компании или имени контакта возвращает результаты без заметной задержки (воспринимается как мгновенный)
- **SC-005**: При удалении компании все связанные заметки, вложения и активности удаляются автоматически — ни одна «осиротевшая» запись не остаётся в системе
- **SC-006**: История изменений схемы полностью воспроизводима: новая среда, развёрнутая по той же истории изменений, идентична существующей

## Clarifications

### Session 2026-05-24

- Q: Что происходит со Сделками при удалении Аккаунта? → A: account_id на сделке становится NULL, сделка сохраняется без привязки к аккаунту
- Q: Какие значения хранить для ролей пользователей в ENUM? → A: английские коды `admin`, `bdm`, `viewer`
- Q: Уникален ли email контакта? → A: нет, дубли допустимы; поле индексируется только для ускорения поиска
- Q: Обязателен ли Аккаунт при создании Сделки? → A: нет, account_id опциональный — Сделка может существовать без Аккаунта

## Assumptions

- Используется реляционная база данных с поддержкой UUID, транзакций и триггеров
- Хранение файлов (фото, вложения) — на локальной файловой системе; в схему вносится только путь к файлу
- Контакт может существовать без привязки к компании (account_id опциональный)
- Заметки и вложения не имеют собственной иерархии — каждая запись привязана ровно к одной сущности
- Фото контакта — отдельный атрибут (один файл на контакт), не является «вложением» в общем смысле
- Начальный набор данных включает только участников команды; тестовые компании/сделки не добавляются
- Сессионная таблица управляется библиотекой авторизации; приложение не работает с ней напрямую
