## User Scenarios & Testing *(mandatory)*

### User Story 1 — Блокировка запрещённых действий (Priority: P1)

Пользователь с ролью bdm или viewer пытается выполнить действие, которое его роль не разрешает. Система немедленно отклоняет запрос с кодом 403 и сообщением об ошибке, не выполняя никаких изменений в данных.

**Why this priority**: Основная ценность RBAC — защита данных от несанкционированных изменений. Без этой проверки вся ролевая модель теряет смысл.

**Independent Test**: Отправить DELETE-запрос от имени bdm и POST/PUT/DELETE от имени viewer — система возвращает 403 с корректным JSON-телом, данные остаются без изменений.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью bdm авторизован, **When** он отправляет DELETE-запрос к любому ресурсу, **Then** возвращается 403 с телом `{ "error": "Forbidden", "message": "Недостаточно прав для выполнения операции" }`, действие не выполняется
2. **Given** пользователь с ролью viewer авторизован, **When** он отправляет POST, PUT или DELETE запрос, **Then** возвращается 403 с тем же телом, данные не изменяются

---

### User Story 2 — Работа в рамках разрешённых действий (Priority: P2)

Каждый пользователь беспрепятственно выполняет действия, разрешённые его ролью: admin — полный доступ, bdm — чтение и запись без удаления, viewer — только чтение.

**Why this priority**: Пользователи должны иметь возможность работать в рамках своих прав — без этого CRM нефункциональна для команды.

**Independent Test**: Выполнить GET/POST/PUT/DELETE от имени каждой роли согласно матрице доступа — разрешённые запросы выполняются успешно.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin авторизован, **When** он выполняет любой GET/POST/PUT/DELETE запрос к ресурсам CRM, **Then** запрос выполняется успешно
2. **Given** пользователь с ролью bdm авторизован, **When** он выполняет GET, POST или PUT запросы к accounts/contacts/deals/notes/attachments/activities, **Then** запросы выполняются успешно
3. **Given** пользователь с ролью viewer авторизован, **When** он выполняет GET-запрос к любому ресурсу, **Then** запрос выполняется успешно

---

### User Story 3 — Управление пользователями только для Admin (Priority: P3)

Только пользователи с ролью admin могут просматривать список участников команды и изменять их роли. Пользователи с ролью bdm и viewer не имеют доступа к этим операциям.

**Why this priority**: Управление пользователями — административная функция. Изоляция этих операций критична для безопасности системы.

**Independent Test**: Отправить GET /api/v1/users и PATCH /api/v1/users/:id/role от имени bdm и viewer — система возвращает 403.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin авторизован, **When** он запрашивает список пользователей (GET /api/v1/users), **Then** возвращается список всех участников команды
2. **Given** пользователь с ролью admin авторизован, **When** он изменяет роль другого пользователя (PATCH /api/v1/users/:id/role), **Then** роль обновляется и вступает в силу немедленно
3. **Given** пользователь с ролью bdm или viewer авторизован, **When** он обращается к GET /api/v1/users или PATCH /api/v1/users/:id/role, **Then** возвращается 403 Forbidden

---

### User Story 4 — Защита от опасных административных операций (Priority: P4)

Система предотвращает два класса опасных операций: изменение собственной роли любым пользователем и понижение роли последнего администратора в системе.

**Why this priority**: Защищает от случайной или намеренной потери административного доступа к системе, что сделало бы её неуправляемой.

**Independent Test**: Попробовать изменить собственную роль и попробовать изменить роль единственного admin — оба действия отклоняются с ошибкой.

**Acceptance Scenarios**:

1. **Given** любой авторизованный пользователь (включая admin), **When** он пытается изменить собственную роль через PATCH /api/v1/users/:id/role, **Then** операция отклоняется с 403 Forbidden
2. **Given** в системе ровно один пользователь с ролью admin, **When** кто-либо пытается изменить роль этого пользователя, **Then** операция отклоняется с понятным сообщением об ошибке

---

### User Story 5 — Просмотр собственного профиля (Priority: P3)

Любой авторизованный пользователь (независимо от роли) может получить данные своего профиля: имя, email, роль. Это необходимо для отображения информации о пользователе в интерфейсе (F-11).

**Why this priority**: Базовая потребность для любого UI — показать текущего пользователя. Не требует административных прав.

**Independent Test**: Выполнить GET /api/v1/users/me от имени bdm и viewer — возвращается объект с данными текущего пользователя.

**Acceptance Scenarios**:

1. **Given** пользователь с любой ролью авторизован, **When** он выполняет GET /api/v1/users/me, **Then** возвращается объект с его id, name, email, role
2. **Given** пользователь не авторизован, **When** он выполняет GET /api/v1/users/me, **Then** возвращается 401 Unauthorized (обрабатывается middleware из F-02)

---

### Edge Cases

- Что происходит при попытке установить невалидное значение роли? → 400 Bad Request с перечислением допустимых значений
- Что если роль пользователя изменена admin в процессе его работы? → Изменение вступает в силу немедленно при следующем запросе (deserializeUser читает роль из БД при каждом запросе)
- Попытка изменить роль последнего admin → 403 с сообщением "Невозможно изменить роль единственного администратора"
- Попытка изменить свою роль → 403 Forbidden для любой роли, включая admin
- Неавторизованный пользователь пытается обратиться к любому защищённому эндпоинту → 401 Unauthorized (обрабатывается middleware из F-02)
- Если пользователь удалён из таблицы users во время активной сессии → при следующем запросе deserializeUser вернёт false, пользователь автоматически выходит из системы (поведение F-02)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА проверять роль авторизованного пользователя при каждом запросе к защищённым эндпоинтам
- **FR-002**: Система ДОЛЖНА возвращать 403 с телом `{ "error": "Forbidden", "message": "Недостаточно прав для выполнения операции" }` при попытке выполнить действие, не разрешённое ролью
- **FR-003**: Пользователь с ролью admin ДОЛЖЕН иметь доступ ко всем операциям: GET, POST, PUT, DELETE для всех ресурсов
- **FR-004**: Пользователь с ролью bdm ДОЛЖЕН иметь доступ к GET, POST, PUT для ресурсов accounts, contacts, deals, notes, attachments, activities
- **FR-005**: Пользователь с ролью bdm НЕ ДОЛЖЕН иметь доступ к DELETE-операциям ни для одного ресурса
- **FR-006**: Пользователь с ролью viewer ДОЛЖЕН иметь доступ только к GET-запросам для всех ресурсов
- **FR-007**: Пользователь с ролью viewer НЕ ДОЛЖЕН иметь доступ к POST, PUT, DELETE операциям
- **FR-008**: Управление пользователями (GET /api/v1/users, GET /api/v1/users/:id, PATCH /api/v1/users/:id/role) ДОЛЖНО быть доступно только роли admin; создание и удаление пользователей через API не предусмотрено
- **FR-009**: Система ДОЛЖНА запрещать любому пользователю изменение собственной роли
- **FR-010**: Система ДОЛЖНА запрещать изменение роли последнего admin в системе
- **FR-011**: Ролевые проверки ДОЛЖНЫ применяться централизованно через переиспользуемый механизм, а не дублироваться в каждом обработчике
- **FR-012**: GET /api/v1/users/me ДОЛЖЕН быть доступен любому авторизованному пользователю независимо от роли и возвращать id, name, email, role текущего пользователя

### Key Entities

- **Роль (Role)**: Одно из трёх фиксированных значений — `admin`, `bdm`, `viewer`. Хранится в профиле пользователя. Определяет набор разрешённых операций.
- **Пользователь (User)**: Участник команды с назначенной ролью. Роль задаётся при добавлении в систему (seed) и может быть изменена только администратором через PATCH /api/v1/users/:id/role.
- **Матрица доступа (Permission Matrix)**:

  | Операция             | admin | bdm | viewer |
  |----------------------|-------|-----|--------|
  | GET (все ресурсы)    | ✓     | ✓   | ✓      |
  | POST (создание)      | ✓     | ✓   | ✗      |
  | PUT (редактирование) | ✓     | ✓   | ✗      |
  | DELETE (удаление)    | ✓     | ✗   | ✗      |
  | GET /api/v1/users    | ✓     | ✗   | ✗      |
  | PATCH …/role         | ✓     | ✗   | ✗      |
  | GET /api/v1/users/me | ✓     | ✓   | ✓      |

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% запросов, нарушающих матрицу доступа, отклоняются с 403 и корректным JSON-телом без выполнения действия
- **SC-002**: Все 4 члена команды (2 admin, 1 bdm, 1 viewer) могут выполнять разрешённые операции без ошибок доступа
- **SC-003**: Попытка изменить роль последнего admin отклоняется в 100% случаев
- **SC-004**: Попытка изменить собственную роль отклоняется в 100% случаев для любой роли
- **SC-005**: Добавление ролевых проверок к новому эндпоинту выполняется без изменения существующей логики механизма проверок
- **SC-006**: GET /api/v1/users/me возвращает корректный профиль для любого авторизованного пользователя независимо от роли

## Assumptions

- F-02 (Google SSO) реализована: пользователь авторизован, в запросе доступен объект пользователя с полями id, email, name, role
- Роли пользователей заданы при seed-инициализации (F-01): Дмитрий Твердохлебов — admin, Юлия Шевцова — admin, Анастасия Стефанова — bdm, Илья Болховский — viewer
- Список ролей фиксирован (admin/bdm/viewer) — расширение ролей не предусмотрено в MVP
- UI для управления пользователями не входит в эту фичу — только API-эндпоинты (UI — в F-11)
- Роль пользователя всегда актуальна: механизм deserializeUser из F-02 перечитывает запись пользователя из БД при каждом запросе — изменение роли вступает в силу немедленно без повторного входа
- Создание и удаление пользователей через API не предусмотрено в MVP — только через seed/миграции
- Ресурсы, к которым применяется матрица доступа: accounts, contacts, deals, notes, attachments, activities (F-04 — F-09)
