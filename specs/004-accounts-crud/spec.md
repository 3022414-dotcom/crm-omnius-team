## Clarifications

### Session 2026-07-04

- Q: Поведение PUT при обновлении — только переданные поля или полная замена? → A: Частичное обновление — только переданные поля изменяются, остальные сохраняются
- Q: Формат пагинированного ответа? → A: `{ "data": [...], "total": 42, "page": 1, "limit": 20 }` — стандартный envelope
- Q: Включать ли счётчики связанных объектов в список аккаунтов? → A: Да — `contactsCount` и `dealsCount` в каждом объекте аккаунта

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Создание нового аккаунта (Priority: P1)

Пользователь с ролью admin или bdm создаёт запись о компании — потенциальном клиенте или действующем партнёре. Указывает название (обязательно) и дополнительные реквизиты: отрасль, сайт, телефон, адрес, заметки.

**Why this priority**: Создание аккаунта — точка входа для всей работы с клиентом. Без аккаунтов невозможна работа с контактами, сделками, активностями.

**Independent Test**: Создать аккаунт с минимальными данными (только name) и с полным набором полей — оба должны сохраняться; попытка создания без name должна быть отклонена.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin или bdm авторизован, **When** он создаёт аккаунт с обязательным полем name, **Then** аккаунт создаётся, возвращается 201 с объектом аккаунта, включая автоматически назначенный owner_id
2. **Given** пользователь с ролью admin или bdm авторизован, **When** он создаёт аккаунт с полным набором полей (name, industry, website, phone, address, notes), **Then** все поля сохраняются и возвращаются в ответе
3. **Given** пользователь с ролью admin или bdm авторизован, **When** он пытается создать аккаунт без поля name, **Then** возвращается 400 Bad Request
4. **Given** пользователь с ролью viewer авторизован, **When** он пытается создать аккаунт, **Then** возвращается 403 Forbidden

---

### User Story 2 — Просмотр и поиск аккаунтов (Priority: P2)

Любой авторизованный пользователь просматривает список компаний с постраничной навигацией и может найти нужную компанию по названию. Каждый аккаунт в списке показывает количество связанных контактов и сделок.

**Why this priority**: Просмотр списка — базовая рабочая задача для всей команды. Счётчики дают быстрое представление о «наполненности» аккаунта без перехода внутрь.

**Independent Test**: Получить список аккаунтов — возвращается envelope `{ data, total, page, limit }` с полями `contactsCount` и `dealsCount` в каждом объекте; поиск по части названия возвращает только совпадающие аккаунты.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь (любая роль), **When** он запрашивает список аккаунтов без параметров, **Then** возвращается `{ "data": [...], "total": N, "page": 1, "limit": 20 }` с первой страницей и полями `contactsCount`, `dealsCount` в каждом объекте
2. **Given** авторизованный пользователь, **When** он запрашивает список с параметрами page=2&limit=10, **Then** возвращается вторая страница из не более чем 10 аккаунтов
3. **Given** авторизованный пользователь, **When** он ищет аккаунты по части названия (например, "омниус"), **Then** возвращаются все аккаунты, название которых содержит это слово (без учёта регистра), с корректными счётчиками
4. **Given** авторизованный пользователь, **When** поиск не даёт результатов, **Then** возвращается `{ "data": [], "total": 0, "page": 1, "limit": 20 }` (не ошибка)

---

### User Story 3 — Редактирование аккаунта (Priority: P3)

Пользователь с ролью admin или bdm обновляет отдельные поля существующей компании — исправляет реквизиты, добавляет новую информацию. Переданные поля обновляются; остальные остаются без изменений.

**Why this priority**: Данные о компаниях меняются — важно поддерживать актуальность без риска затереть поля, которые не редактировались.

**Independent Test**: Отправить обновление только с одним полем (например, phone) — только оно изменяется, остальные поля сохраняют прежние значения. Просмотр до и после подтверждает это.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin или bdm авторизован, **When** он отправляет обновление с одним или несколькими полями, **Then** только переданные поля изменяются, остальные остаются без изменений; возвращается 200 с полным обновлённым объектом
2. **Given** пользователь с ролью admin или bdm авторизован, **When** он пытается обновить несуществующий аккаунт, **Then** возвращается 404 Not Found
3. **Given** пользователь с ролью viewer авторизован, **When** он пытается обновить аккаунт, **Then** возвращается 403 Forbidden
4. **Given** пользователь с ролью admin или bdm авторизован, **When** он пытается обновить name пустой строкой, **Then** возвращается 400 Bad Request

---

### User Story 4 — Удаление аккаунта (Priority: P4)

Пользователь с ролью admin удаляет компанию из системы. Система автоматически обрабатывает связанные данные: сделки, заметки, вложения и активности удаляются, контакты сохраняются (с обнулением ссылки на аккаунт).

**Why this priority**: Удаление — редкая но необходимая операция для очистки данных. Каскадное поведение критично для целостности данных.

**Independent Test**: Удалить аккаунт с привязанными данными — аккаунт исчезает, связанные контакты остаются (account_id = null), сделки/заметки/вложения/активности удаляются.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin авторизован, **When** он удаляет существующий аккаунт, **Then** возвращается 204 No Content, аккаунт исчезает из списка
2. **Given** аккаунт имеет связанные контакты, **When** admin удаляет аккаунт, **Then** контакты остаются в системе, но их ссылка на аккаунт становится пустой
3. **Given** аккаунт имеет связанные сделки, заметки, вложения, активности, **When** admin удаляет аккаунт, **Then** все перечисленные объекты удаляются вместе с аккаунтом
4. **Given** пользователь с ролью bdm или viewer авторизован, **When** он пытается удалить аккаунт, **Then** возвращается 403 Forbidden

---

### Edge Cases

- Создание аккаунта с тем же названием, что у существующего → разрешено (уникальность по name не требуется)
- Поиск с пустой строкой → возвращается полный список (как без параметра search)
- Параметр limit > 100 → применяется как 100 (максимум)
- Параметр page = 0 или отрицательный → возвращается первая страница
- Удаление несуществующего аккаунта → 404 Not Found
- Обновление name пустой строкой → 400 Bad Request
- Обновление с пустым телом запроса → 200, данные без изменений

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА позволять пользователям с ролью admin и bdm создавать аккаунты с обязательным полем «название»
- **FR-002**: Система ДОЛЖНА автоматически назначать создателя аккаунта его владельцем (owner) при создании
- **FR-003**: Система ДОЛЖНА возвращать список аккаунтов в формате `{ "data": [...], "total": N, "page": N, "limit": N }` с постраничной навигацией (страница по умолчанию: 1, размер страницы по умолчанию: 20, максимум: 100)
- **FR-004**: Система ДОЛЖНА поддерживать поиск аккаунтов по названию без учёта регистра
- **FR-005**: Система ДОЛЖНА обновлять аккаунт частично — только переданные поля изменяются, остальные сохраняют текущие значения
- **FR-006**: Система ДОЛЖНА позволять пользователям с ролью admin удалять аккаунты
- **FR-007**: При удалении аккаунта система ДОЛЖНА обнулять ссылку на аккаунт у всех связанных контактов (контакты остаются в системе)
- **FR-008**: При удалении аккаунта система ДОЛЖНА автоматически удалять все связанные сделки, заметки, вложения и активности
- **FR-009**: Система ДОЛЖНА отклонять создание аккаунта без поля «название» с кодом 400; обновление name пустой строкой — тоже 400
- **FR-010**: Система ДОЛЖНА отклонять попытки создания, редактирования или удаления аккаунтов пользователями без соответствующих прав с кодом 403
- **FR-011**: Каждый объект аккаунта в ответах API ДОЛЖЕН включать поля `contactsCount` (количество связанных контактов) и `dealsCount` (количество связанных сделок)

### Key Entities

- **Аккаунт (Account)**: Запись о компании или организации. Поля: название (обязательно), отрасль, веб-сайт, телефон, адрес, заметки, владелец, дата создания, дата обновления. Производные поля: `contactsCount`, `dealsCount` (вычисляются из связанных объектов).
- **Владелец (Owner)**: Участник команды, создавший аккаунт. Назначается автоматически, не может быть изменён через API в рамках этой фичи.
- **Связанные объекты**: Контакты (при удалении аккаунта теряют привязку, но остаются), Сделки / Заметки / Вложения / Активности (при удалении аккаунта удаляются каскадно).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% запросов на создание аккаунта без обязательного поля name отклоняются с кодом 400
- **SC-002**: 100% запросов от viewer на создание/редактирование/удаление отклоняются с кодом 403
- **SC-003**: Поиск по названию возвращает релевантные результаты без учёта регистра в 100% случаев
- **SC-004**: При удалении аккаунта ни один связанный контакт не теряется из системы
- **SC-005**: При удалении аккаунта все связанные сделки, заметки, вложения и активности исчезают из системы
- **SC-006**: Список аккаунтов возвращается в формате `{ data, total, page, limit }` с корректными значениями `contactsCount` и `dealsCount` для каждого аккаунта
- **SC-007**: Частичное обновление аккаунта изменяет только переданные поля — все остальные поля остаются без изменений в 100% случаев

## Assumptions

- F-01 (схема БД) реализована: таблица `accounts` уже существует со всеми полями; каскадные правила для FK настроены в БД
- F-02 (Google SSO) реализована: все запросы к `/api/v1/*` требуют аутентификации
- F-03 (RBAC) реализована: middleware `requireRole` доступен и применяется к роутам
- Поле `owner_id` устанавливается автоматически = текущему пользователю; изменение владельца через API не предусмотрено в MVP
- Поиск выполняется только по полю «название» (name); поиск по другим полям — в бэклоге
- Сортировка по умолчанию — по дате создания (newest first)
- Счётчики `contactsCount` и `dealsCount` возвращаются как в списке аккаунтов (GET /accounts), так и при просмотре отдельного аккаунта (GET /accounts/:id)
- Ответ при создании и редактировании аккаунта (POST/PUT) НЕ включает счётчики — только собственные поля (счётчики = 0 для нового аккаунта)
- UI для предупреждения о каскадном удалении — задача F-11; в F-04 реализуется только API
