# Feature Specification: Контакты (Contacts)

**Feature Branch**: `005-contacts-crud`

**Created**: 2026-07-04

**Status**: Draft

**Input**: User description: "F-05 Контакты (Contacts) — CRUD для физических лиц, привязанных к аккаунтам. Включает загрузку фото."

## Clarifications

### Session 2026-07-04

- Q: Поведение PUT при редактировании — только переданные поля или полная замена? → A: Частичное обновление — только переданные поля изменяются, остальные сохраняются
- Q: Формат ответа GET /api/v1/accounts/:id/contacts — paginated envelope или простой массив? → A: Пагинированный envelope `{ "data": [...], "total": N, "page": 1, "limit": 20 }` — единообразно с остальными списками
- Q: Поведение при указании несуществующего account_id на create/update? → A: 400 Bad Request с явной проверкой существования аккаунта перед INSERT/UPDATE

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Создание контакта (Priority: P1)

Пользователь с ролью admin или bdm создаёт карточку контактного лица. Указывает имя и фамилию (обязательно), а также дополнительные данные: email, телефон, должность. Может сразу привязать контакт к существующему аккаунту или оставить без привязки.

**Why this priority**: Создание контакта — точка входа для работы с людьми (персонами). Без контактов невозможна работа со сделками, активностями и полная картина аккаунта.

**Independent Test**: Создать контакт только с именем и фамилией — должен сохраниться; попытка без first_name или last_name должна быть отклонена; viewer не может создать.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin или bdm авторизован, **When** он создаёт контакт с обязательными полями first_name и last_name, **Then** контакт создаётся, возвращается 201 с объектом контакта, включая автоматически назначенный owner_id
2. **Given** пользователь с ролью admin или bdm авторизован, **When** он создаёт контакт с полным набором полей (first_name, last_name, email, phone, position, account_id), **Then** все поля сохраняются и возвращаются в ответе
3. **Given** пользователь с ролью admin или bdm авторизован, **When** он создаёт контакт без обязательного поля first_name или last_name, **Then** возвращается 400 Bad Request
4. **Given** пользователь с ролью viewer авторизован, **When** он пытается создать контакт, **Then** возвращается 403 Forbidden
5. **Given** пользователь с ролью admin или bdm авторизован, **When** он создаёт контакт без account_id, **Then** контакт создаётся успешно (привязка к аккаунту не обязательна)
6. **Given** пользователь с ролью admin или bdm авторизован, **When** он указывает account_id несуществующего аккаунта, **Then** возвращается 400 Bad Request с сообщением «Аккаунт не найден»

---

### User Story 2 — Просмотр и поиск контактов (Priority: P2)

Любой авторизованный пользователь просматривает список контактов с поиском по имени, фамилии или email. Также можно просматривать все контакты конкретного аккаунта. Каждый контакт показывается с полными данными, включая фото если оно есть.

**Why this priority**: Просмотр и поиск — ежедневная задача. Возможность быстро найти нужного человека критична для работы с клиентами.

**Independent Test**: GET /api/v1/contacts возвращает список с envelope `{ data, total, page, limit }`; GET /api/v1/contacts?search=иванов возвращает только совпадающих; GET /api/v1/accounts/:id/contacts — пагинированный список контактов аккаунта; GET /api/v1/contacts/:id — конкретный контакт или 404.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь (любая роль), **When** он запрашивает список контактов без параметров, **Then** возвращается постраничный список с envelope `{ "data": [...], "total": N, "page": 1, "limit": 20 }`
2. **Given** авторизованный пользователь, **When** он ищет контактов по части имени, фамилии или email (без учёта регистра), **Then** возвращаются только совпадающие контакты
3. **Given** авторизованный пользователь, **When** он запрашивает контакты конкретного аккаунта, **Then** возвращается пагинированный список `{ "data": [...], "total": N, "page": 1, "limit": 20 }` с контактами, привязанными к этому аккаунту
4. **Given** авторизованный пользователь, **When** он запрашивает конкретный контакт по ID, **Then** возвращается полный объект контакта
5. **Given** авторизованный пользователь, **When** он запрашивает несуществующий контакт, **Then** возвращается 404 Not Found

---

### User Story 3 — Редактирование контакта (Priority: P3)

Пользователь с ролью admin или bdm обновляет данные контакта — исправляет телефон, меняет должность, привязывает к другому аккаунту. Обновляются только переданные поля, остальные остаются без изменений.

**Why this priority**: Данные контактов меняются. Важно иметь возможность обновить отдельные поля без риска затереть остальные.

**Independent Test**: PUT с одним полем (например, phone) → только это поле изменяется, остальные сохраняют значения. Просмотр до и после подтверждает это.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin или bdm авторизован, **When** он отправляет обновление с одним или несколькими полями, **Then** только переданные поля изменяются, остальные сохраняются; возвращается 200 с полным обновлённым объектом
2. **Given** пользователь с ролью admin или bdm авторизован, **When** он пытается обновить несуществующий контакт, **Then** возвращается 404 Not Found
3. **Given** пользователь с ролью viewer авторизован, **When** он пытается обновить контакт, **Then** возвращается 403 Forbidden
4. **Given** пользователь с ролью admin или bdm авторизован, **When** он пытается установить first_name или last_name пустой строкой, **Then** возвращается 400 Bad Request
5. **Given** пользователь указывает account_id несуществующего аккаунта при обновлении, **When** запрос отправляется, **Then** возвращается 400 Bad Request с сообщением «Аккаунт не найден»

---

### User Story 4 — Управление фотографией контакта (Priority: P4)

Пользователь с ролью admin или bdm загружает фото контактного лица — портрет или деловое фото. Фото хранится отдельно от других вложений. При повторной загрузке старое фото заменяется. Фото можно удалить.

**Why this priority**: Фото делает карточку контакта более персональной и помогает идентификации человека в команде.

**Independent Test**: Загрузить JPEG-файл → photo_path сохраняется, URL возвращается; загрузить текстовый файл → 400; загрузить файл > 5 MB → 413; удалить фото → photo_path = null.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin или bdm авторизован, **When** он загружает изображение (jpeg/jpg/png/webp, до 5 MB) для существующего контакта, **Then** фото сохраняется, в ответе возвращается URL фото, photo_path обновляется в БД
2. **Given** контакт уже имеет фото, **When** пользователь загружает новое фото, **Then** старый файл удаляется, новый сохраняется; в БД обновляется photo_path
3. **Given** пользователь загружает файл неподдерживаемого формата (не jpeg/jpg/png/webp), **When** файл отправляется, **Then** возвращается 400 Bad Request
4. **Given** пользователь загружает файл больше 5 MB, **When** файл отправляется, **Then** возвращается 413 Payload Too Large
5. **Given** контакт имеет фото, **When** пользователь удаляет фото, **Then** файл удаляется с хранилища, photo_path = null в БД, возвращается 200

---

### User Story 5 — Удаление контакта (Priority: P5)

Пользователь с ролью admin удаляет контакт из системы. Если у контакта есть фото — оно удаляется с диска. Все связи контакта со сделками (deal_contacts) удаляются автоматически.

**Why this priority**: Удаление — редкая, но необходимая операция для очистки устаревших данных.

**Independent Test**: Удалить контакт с фото → 204, фото исчезает с диска, GET → 404; связи со сделками удалены; bdm → 403.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin авторизован, **When** он удаляет существующий контакт, **Then** возвращается 204 No Content, контакт исчезает из системы
2. **Given** контакт имеет фото, **When** admin удаляет контакт, **Then** файл фото удаляется с диска
3. **Given** контакт привязан к сделкам через deal_contacts, **When** admin удаляет контакт, **Then** записи в deal_contacts удаляются
4. **Given** пользователь с ролью bdm или viewer авторизован, **When** он пытается удалить контакт, **Then** возвращается 403 Forbidden

---

### Edge Cases

- Создание контакта с тем же email, что у другого — разрешено (уникальность email не требуется)
- Контакт без привязки к аккаунту (account_id = null) — разрешён
- Поиск с пустой строкой → возвращается полный список
- Параметр limit > 100 → применяется как 100; page < 1 → применяется как 1
- Удаление несуществующего контакта → 404 Not Found
- Загрузка фото несуществующему контакту → 404 Not Found
- Удаление фото если photo_path уже null → 200 (идемпотентно)
- При удалении контакта без фото → удаление проходит без ошибки
- Передача несуществующего account_id при создании или редактировании → 400 Bad Request «Аккаунт не найден»
- GET /api/v1/accounts/:id/contacts для несуществующего аккаунта → 404 Not Found

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА позволять пользователям с ролью admin и bdm создавать контакты с обязательными полями «имя» (first_name) и «фамилия» (last_name)
- **FR-002**: Система ДОЛЖНА автоматически назначать создателя контакта его владельцем (owner_id) при создании
- **FR-003**: Система ДОЛЖНА допускать создание контакта без привязки к аккаунту (account_id опционален)
- **FR-004**: Система ДОЛЖНА возвращать список контактов с постраничной навигацией (по умолчанию: страница 1, размер 20, максимум 100) и envelope `{ data, total, page, limit }`
- **FR-005**: Система ДОЛЖНА поддерживать поиск контактов по first_name, last_name, email без учёта регистра
- **FR-006**: Система ДОЛЖНА возвращать список контактов конкретного аккаунта в формате `{ data, total, page, limit }` с постраничной навигацией
- **FR-007**: Система ДОЛЖНА обновлять контакт частично — только переданные поля изменяются, остальные сохраняют текущие значения
- **FR-008**: Система ДОЛЖНА отклонять попытку установить first_name или last_name пустой строкой при создании или редактировании с кодом 400
- **FR-009**: Система ДОЛЖНА позволять загружать одно фото контакта (форматы: jpeg/jpg/png/webp; максимальный размер: 5 MB)
- **FR-010**: При повторной загрузке фото старый файл ДОЛЖЕН автоматически удаляться
- **FR-011**: Система ДОЛЖНА позволять удалять фото контакта (photo_path → null, файл удаляется)
- **FR-012**: Система ДОЛЖНА позволять пользователям с ролью admin удалять контакты
- **FR-013**: При удалении контакта система ДОЛЖНА удалять файл фото с диска (если он существует)
- **FR-014**: Система ДОЛЖНА отклонять операции создания/редактирования/загрузки фото от пользователей без соответствующих прав с кодом 403; удаление — только для admin
- **FR-015**: При передаче account_id система ДОЛЖНА проверять существование аккаунта и возвращать 400 Bad Request с сообщением «Аккаунт не найден» если аккаунт не существует

### Key Entities

- **Контакт (Contact)**: Физическое лицо — клиент или партнёр. Поля: имя (обязательно), фамилия (обязательно), email, телефон, должность, фотография, аккаунт (опционально), владелец, дата создания/обновления.
- **Фото контакта**: Отдельный механизм хранения — не является вложением (attachment). Один файл на контакт. Хранится в изолированной директории.
- **Связь со сделками**: Контакт может участвовать в нескольких сделках (M:N). При удалении контакта все связи удаляются.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% запросов на создание контакта без first_name или last_name отклоняются с кодом 400
- **SC-002**: 100% запросов от viewer на создание/редактирование/удаление отклоняются с кодом 403
- **SC-003**: Поиск по имени, фамилии и email возвращает релевантные результаты без учёта регистра
- **SC-004**: Загрузка файла неподдерживаемого формата отклоняется в 100% случаев с кодом 400
- **SC-005**: Загрузка файла > 5 MB отклоняется в 100% случаев с кодом 413
- **SC-006**: При удалении контакта фото гарантированно удаляется с диска — 0 orphaned файлов
- **SC-007**: Список контактов возвращается в формате `{ data, total, page, limit }` с корректными значениями
- **SC-008**: Частичное обновление контакта изменяет только переданные поля — все остальные поля остаются без изменений в 100% случаев
- **SC-009**: 100% запросов с несуществующим account_id отклоняются с кодом 400

## Assumptions

- F-01 (схема БД) реализована: таблица `contacts` уже существует со всеми полями; таблица `deal_contacts` с CASCADE-удалением по contact_id
- F-02 (Google SSO) реализована: все запросы к `/api/v1/*` требуют аутентификации
- F-03 (RBAC) реализована: middleware `requireRole` доступен
- F-04 (Accounts) реализована: аккаунты существуют для привязки контактов
- Поле owner_id устанавливается автоматически = текущему пользователю; изменение владельца не предусмотрено в MVP
- Сортировка списка контактов по умолчанию — по дате создания (newest first)
- Директория uploads/ уже существует в .gitignore
- Поиск выполняется по полям first_name, last_name, email; поиск по другим полям — в бэклоге
- UI для подтверждения удаления контакта — задача F-11; в F-05 реализуется только API
- deal_contacts удаляются автоматически через FK CASCADE при удалении контакта (БД-уровень)
