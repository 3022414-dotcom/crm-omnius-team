# Feature Specification: Сделки (Deals)

**Feature Branch**: `006-deals-crud`

**Created**: 2026-07-05

**Status**: Draft

**Input**: User description: "F-06 Сделки (Deals) — CRUD для сделок с воронкой продаж, привязкой контактов и фильтрами"

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Создание сделки (Priority: P1)

Пользователь с ролью admin или bdm создаёт новую сделку. Обязательно указывает название. Может сразу задать сумму, предполагаемую дату закрытия и привязать к аккаунту. Этап сделки автоматически устанавливается «Лид» при создании.

**Why this priority**: Создание сделки — точка входа воронки. Без сделок невозможны фильтрация, Kanban (F-10) и отчётность.

**Independent Test**: `POST /api/v1/deals {title:"Новая сделка"}` → 201 с объектом, stage='lead'; без title → 400; viewer → 403.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin или bdm авторизован, **When** он создаёт сделку с обязательным полем title, **Then** сделка создаётся с stage='lead', owner_id = текущий пользователь, возвращается 201 с объектом сделки
2. **Given** пользователь с ролью admin или bdm авторизован, **When** он создаёт сделку с полным набором полей (title, value, close_date, account_id), **Then** все поля сохраняются и возвращаются в ответе
3. **Given** пользователь с ролью admin или bdm авторизован, **When** он создаёт сделку без title или с пустым title, **Then** возвращается 400 Bad Request
4. **Given** пользователь с ролью viewer авторизован, **When** он пытается создать сделку, **Then** возвращается 403 Forbidden
5. **Given** пользователь указывает account_id несуществующего аккаунта, **When** запрос отправлен, **Then** возвращается 400 Bad Request «Аккаунт не найден»
6. **Given** пользователь не указывает account_id, **Then** сделка создаётся без привязки к аккаунту (account_id = null)

---

### User Story 2 — Просмотр и поиск сделок (Priority: P2)

Любой авторизованный пользователь просматривает список сделок с фильтрацией по этапу, аккаунту, владельцу и датам. Может найти нужную сделку по названию. Также просматривает конкретную сделку с её привязанными контактами.

**Why this priority**: Просмотр воронки и поиск сделок — ежедневная задача команды. Без этого невозможна работа с клиентами.

**Independent Test**: `GET /api/v1/deals` → `{data:[...],total:N,page:1,limit:20}`; `?stage=lead` → только лиды; `GET /api/v1/deals/:id` → объект со списком контактов или 404.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь (любая роль), **When** он запрашивает список сделок без параметров, **Then** возвращается постраничный список с envelope `{ "data": [...], "total": N, "page": 1, "limit": 20 }`
2. **Given** авторизованный пользователь, **When** он фильтрует список по stage, account_id, owner_id или диапазону close_date (date_from / date_to), **Then** возвращаются только совпадающие сделки
3. **Given** авторизованный пользователь, **When** он ищет сделки по части названия (без учёта регистра), **Then** возвращаются только совпадающие сделки
4. **Given** авторизованный пользователь, **When** он запрашивает конкретную сделку по ID, **Then** возвращается объект сделки с полями account (id, name), owner (id, name) и массивом привязанных контактов (id, first_name, last_name, photo_path)
5. **Given** авторизованный пользователь, **When** он запрашивает несуществующую сделку, **Then** возвращается 404 Not Found

---

### User Story 3 — Редактирование сделки и смена этапа (Priority: P3)

Пользователь с ролью admin или bdm обновляет данные сделки — исправляет название, меняет сумму, дату закрытия, аккаунт или переводит сделку на следующий этап воронки. Обновляются только переданные поля.

**Why this priority**: Ведение сделок в актуальном состоянии — ключевая работа bdm. Особенно важна смена этапа для отслеживания воронки.

**Independent Test**: `PUT /api/v1/deals/:id {stage:"qualified"}` → 200, stage изменился; невалидный stage → 400; пустой title → 400.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin или bdm авторизован, **When** он обновляет одно или несколько полей сделки, **Then** только переданные поля изменяются, остальные сохраняются; возвращается 200 с обновлённым объектом
2. **Given** пользователь передаёт валидный stage (lead/qualified/proposal/negotiation/won/lost), **When** запрос отправлен, **Then** stage обновляется
3. **Given** пользователь передаёт невалидный stage (не из списка), **When** запрос отправлен, **Then** возвращается 400 Bad Request
4. **Given** пользователь с ролью viewer авторизован, **When** он пытается обновить сделку, **Then** возвращается 403 Forbidden
5. **Given** пользователь передаёт пустой title, **When** запрос отправлен, **Then** возвращается 400 Bad Request

---

### User Story 4 — Управление контактами сделки (Priority: P4)

Пользователь с ролью admin или bdm привязывает и отвязывает контактных лиц от сделки. Один контакт может участвовать в нескольких сделках. Повторная привязка одного контакта не создаёт дубликат.

**Why this priority**: Связь контактов со сделками необходима для полной картины — кто ведёт переговоры, кто принимает решения.

**Independent Test**: `POST /api/v1/deals/:id/contacts {contact_id}` → 201; повторная привязка → 200 (идемпотентно); `DELETE /api/v1/deals/:id/contacts/:contact_id` → 204.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin или bdm авторизован, **When** он привязывает существующий контакт к существующей сделке, **Then** связь создаётся, возвращается 201
2. **Given** контакт уже привязан к сделке, **When** пользователь повторно привязывает тот же контакт, **Then** возвращается 200 без ошибки (идемпотентно, дубликат не создаётся)
3. **Given** пользователь указывает несуществующий contact_id, **When** запрос отправлен, **Then** возвращается 400 Bad Request «Контакт не найден»
4. **Given** пользователь с ролью admin или bdm авторизован, **When** он отвязывает контакт от сделки, **Then** связь удаляется, возвращается 204
5. **Given** пользователь с ролью viewer авторизован, **When** он пытается привязать или отвязать контакт, **Then** возвращается 403 Forbidden

---

### User Story 5 — Удаление сделки (Priority: P5)

Пользователь с ролью admin удаляет сделку из системы. Все связанные данные (привязки контактов, заметки, вложения, активности) удаляются вместе со сделкой.

**Why this priority**: Удаление — редкая, но необходимая операция для очистки некорректных или устаревших данных.

**Independent Test**: `DELETE /api/v1/deals/:id` → 204; GET → 404; bdm → 403.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin авторизован, **When** он удаляет существующую сделку, **Then** возвращается 204 No Content, сделка и все связанные данные исчезают из системы
2. **Given** сделка привязана к контактам через deal_contacts, **When** admin удаляет сделку, **Then** все записи в deal_contacts удаляются
3. **Given** пользователь с ролью bdm или viewer авторизован, **When** он пытается удалить сделку, **Then** возвращается 403 Forbidden
4. **Given** пользователь пытается удалить несуществующую сделку, **When** запрос отправлен, **Then** возвращается 404 Not Found

---

### Edge Cases

- Создание сделки без account_id — разрешено (account_id = null)
- Привязка контакта дважды — идемпотентно, дубликат не создаётся (ON CONFLICT DO NOTHING)
- Попытка установить невалидный stage → 400 Bad Request
- Пустая строка в title → 400 Bad Request
- Фильтр по несуществующему account_id → пустой список (не 404)
- Фильтр по несуществующему owner_id → пустой список
- Параметр limit > 100 → применяется как 100; page < 1 → применяется как 1
- Удаление несуществующей сделки → 404 Not Found
- Попытка отвязать контакт, который не привязан → 204 (идемпотентно)
- Сделка без аккаунта — разрешена на всех этапах воронки
- owner_id в PUT /deals/:id: если указан несуществующий user_id → 400 Bad Request «Пользователь не найден»

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА позволять пользователям с ролью admin и bdm создавать сделки с обязательным полем «название» (title)
- **FR-002**: Система ДОЛЖНА устанавливать stage = 'lead' при создании сделки
- **FR-003**: Система ДОЛЖНА автоматически назначать создателя сделки её владельцем (owner_id) при создании
- **FR-004**: Система ДОЛЖНА допускать создание сделки без привязки к аккаунту (account_id опционален)
- **FR-005**: Система ДОЛЖНА возвращать список сделок с постраничной навигацией (по умолчанию: страница 1, размер 20, максимум 100) и envelope `{ data, total, page, limit }`; каждый объект списка включает account {id, name}, owner {id, name} и contacts_count (integer)
- **FR-006**: Система ДОЛЖНА поддерживать поиск сделок по title (ILIKE, без учёта регистра)
- **FR-007**: Система ДОЛЖНА поддерживать фильтрацию списка по: stage, account_id, owner_id, диапазону close_date (параметры date_from и date_to)
- **FR-008**: Система ДОЛЖНА возвращать в ответе на GET /deals/:id сведения об аккаунте (id, name), владельце (id, name) и массив привязанных контактов (id, first_name, last_name, photo_path)
- **FR-009**: Система ДОЛЖНА обновлять сделку частично — только переданные поля изменяются; обновляемые поля: title, value, close_date, account_id, stage, owner_id (owner_id могут изменить admin и bdm)
- **FR-010**: Система ДОЛЖНА валидировать поле stage: допустимые значения lead/qualified/proposal/negotiation/won/lost; невалидное → 400
- **FR-011**: Система ДОЛЖНА отклонять попытку установить пустой title с кодом 400
- **FR-012**: Система ДОЛЖНА позволять привязывать контакты к сделке (POST /deals/:id/contacts); повторная привязка идемпотентна — 200
- **FR-013**: Система ДОЛЖНА позволять отвязывать контакты от сделки (DELETE /deals/:id/contacts/:contact_id); отвязка незарегистрированного контакта идемпотентна — 204
- **FR-014**: Система ДОЛЖНА позволять пользователям с ролью admin удалять сделки
- **FR-015**: При удалении сделки система ДОЛЖНА каскадно удалять: deal_contacts (DB CASCADE), notes/attachments/activities (app-level, паттерн F-05)
- **FR-016**: Система ДОЛЖНА отклонять операции создания/редактирования/управления контактами от пользователей без соответствующих прав с кодом 403; удаление — только для admin
- **FR-017**: При передаче account_id система ДОЛЖНА проверять существование аккаунта и возвращать 400 «Аккаунт не найден» если не найден
- **FR-018**: При привязке контакта система ДОЛЖНА проверять существование контакта и возвращать 400 «Контакт не найден» если не найден

### Key Entities

- **Сделка (Deal)**: Коммерческая возможность. Поля: название (обязательно), сумма, этап воронки, дата закрытия, аккаунт (опционально), владелец, даты создания/обновления.
- **Этап (Stage)**: Позиция сделки в воронке. Значения: lead → qualified → proposal → negotiation → won/lost.
- **Участники сделки**: Контактные лица, участвующие в сделке (M:N). Один контакт может участвовать в нескольких сделках.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% запросов на создание сделки без title или с пустым title отклоняются с кодом 400
- **SC-002**: 100% запросов с невалидным stage отклоняются с кодом 400
- **SC-003**: 100% запросов от viewer на запись отклоняются с кодом 403
- **SC-004**: Фильтрация по stage, account_id, owner_id возвращает только соответствующие сделки
- **SC-005**: Повторная привязка контакта не создаёт дублирующую запись в deal_contacts — 0 дубликатов
- **SC-006**: При удалении сделки все зависимые данные (deal_contacts, notes, attachments, activities) удаляются — 0 orphaned записей

## Clarifications

### Session 2026-07-05

- Q: Включает ли GET /deals (список) поле contacts_count на каждый объект сделки? → A: Да — contacts_count (integer) включён в каждый объект списка для совместимости с Kanban (F-10)
- Q: Можно ли изменить owner_id через PUT /deals/:id? → A: Да — admin и bdm могут изменить owner_id; owner_id входит в UPDATABLE_FIELDS (в отличие от паттерна F-04/F-05)

## Assumptions

- Поиск по title работает как «содержит» (ILIKE), без полнотекстового поиска
- Сортировка списка по умолчанию: created_at DESC
- Ответ GET /deals/:id включает контакты как массив упрощённых объектов (id, first_name, last_name, photo_path), не полных объектов
- Ответ GET /deals (список) включает account {id, name}, owner {id, name} и contacts_count (integer) для совместимости с Kanban (F-10)
- deal_contacts удаляются через DB CASCADE при удалении сделки (FK ON DELETE CASCADE на deal_id)
- notes/attachments/activities удаляются на уровне приложения (полиморфные таблицы без FK, паттерн F-05 deleteContact)
- Параметры date_from и date_to фильтруют по close_date (DATE), граничные значения включительно
