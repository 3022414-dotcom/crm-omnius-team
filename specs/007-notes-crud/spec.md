## User Scenarios & Testing *(mandatory)*

### User Story 1 — Создание заметки (Priority: P1)

Пользователь с ролью admin или bdm добавляет текстовую заметку к аккаунту, контакту или сделке. Заметка содержит произвольный текст и привязывается к конкретной сущности. Автор фиксируется автоматически.

**Why this priority**: Заметки — основной инструмент фиксации договорённостей, звонков и статусов. Без них невозможна совместная работа команды по клиентам.

**Independent Test**: `POST /api/v1/notes {entity_type:"account", entity_id:UUID, content:"Звонок состоялся"}` → 201 с объектом заметки, author_id = текущий пользователь; пустой content → 400; viewer → 403.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin или bdm авторизован, **When** он создаёт заметку с валидными entity_type, entity_id и content, **Then** заметка создаётся с author_id = текущий пользователь, возвращается 201 с объектом заметки
2. **Given** пользователь указывает entity_type='contact' и существующий contact_id, **When** заметка создана, **Then** она корректно привязана к контакту
3. **Given** пользователь указывает entity_type='deal' и существующий deal_id, **When** заметка создана, **Then** она корректно привязана к сделке
4. **Given** пользователь передаёт пустой или отсутствующий content, **When** запрос отправлен, **Then** возвращается 400 Bad Request
5. **Given** пользователь указывает несуществующий entity_id, **When** запрос отправлен, **Then** возвращается 404 Not Found
6. **Given** пользователь с ролью viewer авторизован, **When** он пытается создать заметку, **Then** возвращается 403 Forbidden

---

### User Story 2 — Просмотр заметок сущности (Priority: P2)

Любой авторизованный пользователь просматривает список заметок, привязанных к конкретному аккаунту, контакту или сделке. Заметки отображаются от новых к старым, каждая со сведениями об авторе.

**Why this priority**: Просмотр истории заметок — ежедневная задача при работе с клиентами. Необходим для понимания контекста переговоров.

**Independent Test**: `GET /api/v1/accounts/:id/notes` → список заметок sorted by created_at DESC, каждая содержит author {id, name}; несуществующий id → 404; пустая история → [].

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь (любая роль), **When** он запрашивает заметки существующего аккаунта, **Then** возвращается список заметок, отсортированных по created_at DESC, каждая содержит id, content, author {id, name}, created_at, updated_at
2. **Given** авторизованный пользователь, **When** он запрашивает заметки существующего контакта (`GET /api/v1/contacts/:id/notes`), **Then** возвращаются заметки этого контакта
3. **Given** авторизованный пользователь, **When** он запрашивает заметки существующей сделки (`GET /api/v1/deals/:id/notes`), **Then** возвращаются заметки этой сделки
4. **Given** авторизованный пользователь, **When** у сущности нет заметок, **Then** возвращается пустой массив `[]`
5. **Given** авторизованный пользователь, **When** он запрашивает заметки несуществующей сущности, **Then** возвращается 404 Not Found

---

### User Story 3 — Редактирование заметки (Priority: P3)

Автор заметки или пользователь с ролью admin изменяет текст существующей заметки. Изменяется только поле content; привязка к сущности и автор остаются неизменными.

**Why this priority**: Исправление ошибок и дополнение заметок — необходимая часть рабочего процесса команды.

**Independent Test**: `PUT /api/v1/notes/:id {content:"Обновлено"}` → 200 с обновлённым объектом (автор или admin); не автор и не admin → 403; пустой content → 400.

**Acceptance Scenarios**:

1. **Given** автор заметки авторизован, **When** он обновляет content заметки, **Then** content изменяется, возвращается 200 с обновлённым объектом заметки
2. **Given** пользователь с ролью admin авторизован, **When** он обновляет чужую заметку, **Then** content изменяется, возвращается 200
3. **Given** пользователь не является автором и не admin, **When** он пытается обновить заметку, **Then** возвращается 403 Forbidden
4. **Given** пользователь передаёт пустой content, **When** запрос отправлен, **Then** возвращается 400 Bad Request
5. **Given** пользователь пытается обновить несуществующую заметку, **When** запрос отправлен, **Then** возвращается 404 Not Found

---

### User Story 4 — Удаление заметки (Priority: P4)

Автор заметки или пользователь с ролью admin удаляет заметку. Прочие пользователи не могут удалять чужие заметки.

**Why this priority**: Управление заметками (удаление ошибочных или устаревших) необходимо для поддержания актуальности данных.

**Independent Test**: `DELETE /api/v1/notes/:id` → 204 (автор или admin); bdm не-автор → 403; несуществующая → 404.

**Acceptance Scenarios**:

1. **Given** автор заметки (с любой ролью) авторизован, **When** он удаляет свою заметку, **Then** возвращается 204 No Content, заметка исчезает из списка
2. **Given** пользователь с ролью admin авторизован, **When** он удаляет любую заметку (не свою), **Then** возвращается 204 No Content
3. **Given** пользователь не является автором и не admin, **When** он пытается удалить чужую заметку, **Then** возвращается 403 Forbidden
4. **Given** пользователь пытается удалить несуществующую заметку, **When** запрос отправлен, **Then** возвращается 404 Not Found

---

### Edge Cases

- Пустой content при создании или редактировании → 400 Bad Request
- Невалидный entity_type (не account/contact/deal) → 400 Bad Request
- entity_id не соответствует существующей сущности указанного entity_type → 404 Not Found
- Редактирование или удаление чужой заметки (не автором, не admin) → 403 Forbidden
- Запрос заметок несуществующей сущности → 404 Not Found
- Сущность без заметок → пустой массив `[]` (не 404)
- viewer не может создавать, редактировать или удалять заметки — только читать
- Заметки удаляются каскадно при удалении родительской сущности (уже обеспечивается в F-04, F-05, F-06)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА позволять пользователям с ролью admin и bdm создавать заметки с обязательными полями entity_type, entity_id и content
- **FR-002**: Система ДОЛЖНА отклонять создание или редактирование заметки с пустым content с кодом 400
- **FR-003**: Система ДОЛЖНА проверять существование сущности (entity_type + entity_id) при создании заметки и возвращать 404 если сущность не найдена
- **FR-004**: Система ДОЛЖНА автоматически устанавливать author_id равным id текущего пользователя при создании заметки
- **FR-005**: Система ДОЛЖНА возвращать список заметок сущности через GET /api/v1/accounts/:id/notes, GET /api/v1/contacts/:id/notes, GET /api/v1/deals/:id/notes — в виде простого массива `[...]` (без envelope), отсортированных по created_at DESC; каждая заметка включает author {id, name}
- **FR-006**: Система ДОЛЖНА возвращать 404 при запросе заметок несуществующей сущности
- **FR-007**: Система ДОЛЖНА позволять редактировать content заметки только автору или пользователю с ролью admin; другим — 403
- **FR-008**: Система ДОЛЖНА позволять удалять заметку только автору или пользователю с ролью admin; другим — 403
- **FR-009**: Система ДОЛЖНА отклонять операции создания, редактирования и удаления от пользователей с ролью viewer с кодом 403
- **FR-010**: Система ДОЛЖНА валидировать entity_type: допустимые значения account/contact/deal; невалидное → 400
- **FR-011**: Система ДОЛЖНА возвращать пустой массив при запросе заметок сущности, у которой их нет

### Key Entities

- **Заметка (Note)**: Текстовая запись, привязанная к одной сущности (аккаунт, контакт или сделка). Поля: уникальный идентификатор, тип родительской сущности, идентификатор родительской сущности, содержимое, автор, даты создания и изменения.
- **Автор**: Пользователь системы, создавший заметку. Устанавливается автоматически при создании и не меняется.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% запросов на создание/редактирование с пустым content отклоняются с кодом 400
- **SC-002**: 100% попыток редактирования или удаления чужой заметки (не автором, не admin) отклоняются с кодом 403
- **SC-003**: 100% запросов от viewer на запись отклоняются с кодом 403
- **SC-004**: Заметки в ответе отсортированы по дате создания DESC — 100% запросов
- **SC-005**: При удалении аккаунта, контакта или сделки все связанные заметки удаляются — 0 orphaned записей

## Assumptions

- Список заметок не пагинируется; ответ — простой массив `[...]`, не envelope `{data, total, page, limit}`
- Ответ включает автора как вложенный объект {id, name} — для отображения имени без дополнительных запросов
- entity_type принимает значения: account, contact, deal (соответствует ENUM в таблице notes из F-01)
- Редактирование заметки меняет только content; entity_type, entity_id и author_id неизменны после создания
- Каскадное удаление заметок при удалении родительской сущности уже обеспечивается app-level DELETE в F-04/F-05/F-06
- Маршруты для просмотра заметок добавляются к существующим роутерам accounts.js, contacts.js, deals.js
- Сортировка: created_at DESC
