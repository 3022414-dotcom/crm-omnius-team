# Feature Specification: Вложения (Attachments)

**Feature Branch**: `008-attachments-crud`

**Created**: 2026-07-05

**Status**: Draft

**Input**: User description: "F-08 Вложения (Attachments) — загрузка и хранение файлов к аккаунтам, контактам и сделкам. Полиморфная ассоциация. Локальное хранение (uploads/)."

## Clarifications

### Session 2026-07-05

- Q: Должно ли поле `file_path` (внутренний путь на диске сервера) включаться в API-ответ (upload и list)? → A: Нет — `file_path` остаётся только внутренним полем БД; в API-ответ не включается; доступ к файлу обеспечивает эндпоинт `/api/v1/attachments/:id/download`

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Загрузка вложения (Priority: P1)

Пользователь с ролью admin или bdm загружает файл (документ, таблицу, изображение и т.п.) и прикрепляет его к существующему аккаунту, контакту или сделке. Файл сохраняется на сервере, в системе создаётся запись с метаданными: имя файла, размер, тип, кто загрузил.

**Why this priority**: Загрузка вложений — базовая операция, без которой остальные сценарии (просмотр, скачивание, удаление) невозможны. Это P1 — ядро фичи.

**Independent Test**: `POST /api/v1/attachments` multipart с файлом и `{entity_type:"account", entity_id:UUID}` → 201 с метаданными `{id, file_name, file_size, mime_type, entity_type, entity_id, uploaded_by:{id,name}, created_at}`; файл > 50 MB → 413; viewer → 403; несуществующий entity_id → 404.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin или bdm авторизован, **When** он загружает файл с валидными entity_type и entity_id, **Then** файл сохраняется, возвращается 201 с метаданными вложения включая uploaded_by {id, name}
2. **Given** файл прикрепляется к контакту, **When** запрос выполнен, **Then** вложение корректно привязано к entity_type='contact'
3. **Given** файл прикрепляется к сделке, **When** запрос выполнен, **Then** вложение корректно привязано к entity_type='deal'
4. **Given** файл превышает 50 MB, **When** пользователь пытается загрузить его, **Then** возвращается 413 Payload Too Large
5. **Given** пользователь указывает несуществующий entity_id, **When** запрос отправлен, **Then** возвращается 404 Not Found
6. **Given** пользователь с ролью viewer, **When** он пытается загрузить файл, **Then** возвращается 403 Forbidden

---

### User Story 2 — Просмотр вложений сущности (Priority: P2)

Любой авторизованный пользователь просматривает список вложений, прикреплённых к конкретному аккаунту, контакту или сделке. Возвращаются только метаданные файлов (без содержимого).

**Why this priority**: Просмотр списка файлов необходим для навигации и поиска нужного вложения перед скачиванием.

**Independent Test**: `GET /api/v1/accounts/:id/attachments` → массив с метаданными, каждый с uploaded_by:{id,name}; несуществующий entity → 404; нет вложений → [].

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь (любая роль), **When** он запрашивает вложения существующего аккаунта, **Then** возвращается список вложений с метаданными: id, file_name, file_size, mime_type, entity_type, entity_id, uploaded_by {id, name}, created_at
2. **Given** авторизованный пользователь, **When** запрашивает вложения контакта (`GET /api/v1/contacts/:id/attachments`), **Then** возвращаются вложения этого контакта
3. **Given** авторизованный пользователь, **When** запрашивает вложения сделки (`GET /api/v1/deals/:id/attachments`), **Then** возвращаются вложения этой сделки
4. **Given** у сущности нет вложений, **When** запрашивается список, **Then** возвращается пустой массив `[]`
5. **Given** пользователь запрашивает вложения несуществующей сущности, **When** запрос отправлен, **Then** возвращается 404 Not Found

---

### User Story 3 — Скачивание файла (Priority: P3)

Любой авторизованный пользователь скачивает конкретный файл по его идентификатору. Файл отправляется с правильными HTTP-заголовками, позволяющими браузеру сохранить его под оригинальным именем.

**Why this priority**: Скачивание — ключевая цель хранения файлов. Без скачивания вложения бесполезны.

**Independent Test**: `GET /api/v1/attachments/:id/download` → поток файла с заголовком `Content-Disposition: attachment; filename="..."` и корректным Content-Type; несуществующее вложение → 404; файл отсутствует на диске → 404.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** он запрашивает скачивание существующего вложения, **Then** файл отправляется с заголовком `Content-Disposition: attachment; filename="<file_name>"` и Content-Type, соответствующим mime_type
2. **Given** физический файл отсутствует на диске (запись в БД есть), **When** пользователь запрашивает скачивание, **Then** возвращается 404 Not Found
3. **Given** пользователь запрашивает несуществующее вложение (нет записи в БД), **When** запрос отправлен, **Then** возвращается 404 Not Found

---

### User Story 4 — Удаление вложения (Priority: P4)

Пользователь с ролью admin удаляет вложение: файл удаляется с диска, запись удаляется из базы данных. BDM не может удалять вложения (в соответствии с общей политикой ролей).

**Why this priority**: Управление файлами (удаление устаревших или ошибочно загруженных) необходимо для поддержания порядка в системе.

**Independent Test**: `DELETE /api/v1/attachments/:id` → 204 (admin); bdm → 403; несуществующее → 404; файл физически отсутствует на диске после успешного удаления.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin, **When** он удаляет существующее вложение, **Then** возвращается 204, файл удаляется с диска, запись удаляется из БД
2. **Given** пользователь с ролью bdm, **When** он пытается удалить вложение, **Then** возвращается 403 Forbidden
3. **Given** пользователь с ролью viewer, **When** он пытается удалить вложение, **Then** возвращается 403 Forbidden
4. **Given** пользователь пытается удалить несуществующее вложение, **When** запрос отправлен, **Then** возвращается 404 Not Found

---

### Edge Cases

- Файл > 50 MB при загрузке → 413 Payload Too Large
- Диск переполнен во время загрузки → 500 с понятным сообщением об ошибке
- entity_type не входит в допустимый список (account/contact/deal) → 400 Bad Request
- entity_id не соответствует существующей сущности → 404 Not Found
- Физический файл отсутствует на диске при скачивании → 404 Not Found
- Сущность без вложений → пустой массив `[]` (не 404)
- Запрос вложений несуществующей сущности → 404 (не пустой массив)
- При удалении родительской сущности → файлы и записи вложений удаляются каскадно
- Загрузка без entity_type или entity_id → 400 Bad Request
- Фото контакта (photo_path) — отдельный механизм F-05, не является вложением F-08

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА позволять пользователям с ролью admin и bdm загружать файлы через multipart/form-data и прикреплять их к существующим аккаунтам, контактам или сделкам
- **FR-002**: Система ДОЛЖНА сохранять файл и создавать запись с метаданными: оригинальное имя файла, путь на диске (внутренний), размер, MIME-тип, привязка к сущности, автор загрузки; в API-ответ возвращаются: id, file_name, file_size, mime_type, entity_type, entity_id, uploaded_by {id, name}, created_at — поле file_path в ответ НЕ включается
- **FR-003**: Система ДОЛЖНА отклонять загрузку файлов размером более 50 MB с кодом 413
- **FR-004**: Система ДОЛЖНА валидировать entity_type: допустимые значения account/contact/deal; невалидное → 400
- **FR-005**: Система ДОЛЖНА проверять существование сущности (entity_type + entity_id) при загрузке и возвращать 404 если сущность не найдена
- **FR-006**: Система ДОЛЖНА возвращать список вложений сущности через GET /api/v1/accounts/:id/attachments, GET /api/v1/contacts/:id/attachments, GET /api/v1/deals/:id/attachments — в виде массива метаданных, отсортированных по created_at DESC; каждый объект содержит: id, file_name, file_size, mime_type, entity_type, entity_id, uploaded_by {id, name}, created_at; поле file_path в ответ НЕ включается
- **FR-007**: Система ДОЛЖНА возвращать 404 при запросе вложений несуществующей сущности
- **FR-008**: Система ДОЛЖНА возвращать пустой массив при запросе вложений сущности, у которой их нет
- **FR-009**: Система ДОЛЖНА позволять любому авторизованному пользователю скачивать файл через GET /api/v1/attachments/:id/download с заголовком Content-Disposition и корректным Content-Type
- **FR-010**: Система ДОЛЖНА возвращать 404 при скачивании несуществующего вложения или если физический файл отсутствует на диске
- **FR-011**: Система ДОЛЖНА позволять только пользователю с ролью admin удалять вложение — файл удаляется с диска, запись удаляется из БД; bdm и viewer → 403

### Key Entities

- **Вложение (Attachment)**: Файл, загруженный пользователем и привязанный к одной сущности. Хранимые поля: id, entity_type, entity_id, file_name, file_path (внутренний, в API не раскрывается), file_size, mime_type, uploaded_by (FK → users), created_at. В API-ответ включаются все поля кроме file_path.
- **Автор загрузки (uploaded_by)**: Пользователь, загрузивший файл. Устанавливается автоматически из текущей сессии, неизменен после создания.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% файлов размером более 50 MB отклоняются с кодом 413 до сохранения на диск
- **SC-002**: 100% попыток удаления от пользователей без роли admin отклоняются с кодом 403
- **SC-003**: 100% попыток загрузки от viewer отклоняются с кодом 403
- **SC-004**: Скачивание возвращает корректный Content-Disposition с оригинальным именем файла — 100% запросов
- **SC-005**: При удалении вложения файл физически отсутствует на диске — 0 orphaned-файлов
- **SC-006**: При удалении аккаунта, контакта или сделки все прикреплённые файлы и записи удаляются — 0 orphaned-вложений

## Assumptions

- Список вложений не пагинируется; ответ — простой массив `[...]`, sorted by created_at DESC
- Допустимые типы файлов не ограничиваются по MIME-типу — принимаются все файлы; ограничение только по размеру (50 MB)
- Путь хранения: `uploads/{entity_type}s/{entity_id}/{uuid}_{original_name}` (например: `uploads/accounts/{id}/abc123_договор.pdf`)
- Нет операции редактирования — файл нельзя заменить, только удалить и загрузить заново
- Каскадное удаление вложений при удалении родительской сущности обеспечивается app-level DELETE в F-04/F-05/F-06 (аналогично F-07)
- Фото контакта (`photo_path`) — отдельный механизм F-05, не является вложением и не входит в эту фичу
- Маршруты GET /:id/attachments добавляются к существующим роутерам accounts.js, contacts.js, deals.js
- multer уже установлен в проекте (используется в F-05 для загрузки фото контакта)
- uploaded_by в ответе — вложенный объект {id, name} для отображения без дополнительных запросов
- Запись не содержит поле updated_at (файл нельзя изменить — только загрузить или удалить)
