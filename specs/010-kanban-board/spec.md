# Feature Specification: Kanban-доска

**Feature Branch**: `010-kanban-board`

**Created**: 2026-07-05

**Status**: Draft

**Input**: User description: "F-10 Kanban-доска — визуальное управление сделками по стадиям. Колонки соответствуют стадиям deal.stage: lead/qualified/proposal/negotiation/won/lost. Перетаскивание карточки сделки меняет stage. Фильтрация по owner. Быстрый просмотр карточки (сумма, аккаунт, владелец). Только backend API."

## Clarifications

### Session 2026-07-05

- Q: Как сортируются сделки внутри каждой колонки Kanban? → A: По дате создания DESC (created_at DESC) — новые сделки сверху; аналогично всем другим списковым эндпоинтам проекта

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Просмотр Kanban-доски (Priority: P1)

Любой авторизованный пользователь открывает Kanban-доску и видит все сделки компании, распределённые по стадиям воронки продаж. Каждая карточка содержит ключевую информацию о сделке: название, сумму, связанный аккаунт, владельца и дату закрытия.

**Why this priority**: Просмотр доски — основная ценность Kanban. Без него перемещение карточек и фильтрация бессмысленны. P1 — ядро фичи.

**Independent Test**: Запрос данных Kanban-доски → возвращается объект с 6 ключами (lead, qualified, proposal, negotiation, won, lost), каждый содержит массив карточек; пустые стадии возвращают []; каждая карточка содержит id, title, value, account {name}, owner {name}, close_date, contacts_count.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь (любая роль), **When** он запрашивает Kanban-доску, **Then** возвращается объект с 6 стадиями в порядке: lead → qualified → proposal → negotiation → won → lost; каждая стадия содержит массив карточек сделок (или пустой массив)
2. **Given** в системе есть сделки в разных стадиях, **When** пользователь запрашивает доску, **Then** каждая карточка содержит: id, title, value (сумма), account (объект с name), owner (объект с id и name), close_date, contacts_count (количество связанных контактов)
3. **Given** в одной или нескольких стадиях нет сделок, **When** пользователь запрашивает доску, **Then** эти стадии возвращают пустой массив [], а не ошибку
4. **Given** сделки в стадии won или lost, **When** пользователь запрашивает доску, **Then** эти сделки присутствуют на доске (архивирование не предусмотрено)
5. **Given** неавторизованный пользователь, **When** он запрашивает Kanban-доску, **Then** возвращается 401 Unauthorized

---

### User Story 2 — Перемещение сделки по стадиям (Priority: P2)

Пользователь с ролью admin или bdm переводит сделку из одной стадии воронки в другую. Это отражает прогресс переговоров или изменение статуса сделки.

**Why this priority**: Перемещение карточек — основное взаимодействие с Kanban. Без него доска доступна только для чтения и теряет свою главную ценность как инструмент управления.

**Independent Test**: Запрос на изменение стадии существующей сделки → 200 с обновлённым объектом сделки; невалидная стадия → 400; несуществующая сделка → 404; viewer → 403.

**Acceptance Scenarios**:

1. **Given** пользователь с ролью admin или bdm, **When** он меняет стадию существующей сделки на валидное значение, **Then** возвращается 200 с обновлённым объектом сделки; поле stage отражает новое значение
2. **Given** пользователь указывает стадию, не входящую в список lead/qualified/proposal/negotiation/won/lost, **When** запрос отправлен, **Then** возвращается 400 Bad Request
3. **Given** пользователь пытается изменить стадию несуществующей сделки, **When** запрос отправлен, **Then** возвращается 404 Not Found
4. **Given** пользователь с ролью viewer, **When** он пытается изменить стадию сделки, **Then** возвращается 403 Forbidden

---

### User Story 3 — Фильтрация Kanban по владельцу (Priority: P3)

Любой авторизованный пользователь фильтрует Kanban-доску по конкретному менеджеру, чтобы видеть только его сделки. Это позволяет контролировать загрузку сотрудников и фокусироваться на нужном владельце.

**Why this priority**: Фильтрация — вспомогательная функция. Доска ценна и без неё, но фильтр по владельцу критичен для команды из нескольких менеджеров.

**Independent Test**: Запрос Kanban-доски с параметром owner_id → возвращаются только сделки указанного владельца (все 6 стадий, остальные — пустые массивы); несуществующий owner_id → все стадии возвращают [].

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** он запрашивает доску с параметром owner_id=UUID, **Then** возвращаются только сделки, у которых owner_id совпадает с указанным; структура ответа та же (6 стадий)
2. **Given** пользователь фильтрует по owner_id, у которого нет сделок (или UUID не существует), **When** запрос выполнен, **Then** все 6 стадий возвращают пустые массивы []
3. **Given** пользователь не указывает owner_id, **When** запрашивает доску, **Then** возвращаются сделки всех владельцев

---

### Edge Cases

- Пустая колонка → возвращается `[]`, не ошибка и не `null`
- Сделки в стадии won или lost остаются на доске (архивирования нет)
- Фильтр owner_id с несуществующим UUID → все стадии возвращают []
- Отсутствие фильтра owner_id → все сделки
- account = null (сделка без аккаунта) → account отображается как null в карточке
- Невалидная стадия при перемещении → 400 Bad Request
- Несуществующая сделка при перемещении → 404 Not Found
- viewer пытается изменить стадию → 403 Forbidden

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА предоставлять Kanban-представление сделок через специализированный эндпоинт доступный всем авторизованным пользователям; ответ содержит объект с 6 ключами (lead, qualified, proposal, negotiation, won, lost) в фиксированном порядке, каждый ключ — массив карточек сделок, отсортированных по дате создания DESC (новые сверху)
- **FR-002**: Каждая карточка сделки в Kanban ДОЛЖНА содержать: id, title, value (сумма сделки), account (объект с name или null если сделка без аккаунта), owner (объект с id и name), close_date, contacts_count (количество связанных контактов)
- **FR-003**: Стадии без сделок ДОЛЖНЫ присутствовать в ответе с пустым массивом `[]`; ответ всегда содержит все 6 стадий
- **FR-004**: Система ДОЛЖНА поддерживать опциональный фильтр по owner_id: при указании — возвращаются только сделки данного владельца; без параметра — все сделки
- **FR-005**: Система ДОЛЖНА позволять пользователям с ролью admin и bdm изменять стадию сделки; допустимые значения: lead, qualified, proposal, negotiation, won, lost; невалидное значение → 400 Bad Request; несуществующая сделка → 404; viewer → 403

### Key Entities

- **Kanban-доска**: Представление всех сделок, сгруппированных по стадиям воронки. Не отдельная таблица — агрегация данных существующих сделок.
- **Карточка сделки (Kanban Card)**: Облегчённое представление сделки для доски. Содержит ключевые поля для быстрого просмотра: id, title, value, account (name), owner (id, name), close_date, contacts_count.
- **Стадия (stage)**: Этап воронки продаж. Допустимые значения: lead, qualified, proposal, negotiation, won, lost. Фиксированный порядок для отображения колонок.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Kanban-доска всегда возвращает ровно 6 стадий, включая пустые — 0 отсутствующих ключей в ответе
- **SC-002**: 100% попыток установить невалидную стадию возвращают 400 Bad Request
- **SC-003**: 100% попыток изменить стадию от пользователя с ролью viewer возвращают 403 Forbidden
- **SC-004**: Фильтр по owner_id возвращает только сделки указанного владельца — 0 сделок от других владельцев в результате
- **SC-005**: Карточки всех сделок содержат contacts_count без дополнительных запросов со стороны клиента

## Assumptions

- Kanban — это представление данных deals, не отдельная таблица в БД; никаких новых таблиц не создаётся
- Порядок стадий фиксирован: lead → qualified → proposal → negotiation → won → lost
- Сделки в стадии won и lost остаются на доске (архивирование и скрытие — в бэклоге)
- Карточка не включает полный список контактов — только их количество (contacts_count)
- account может быть null (сделка без привязанного аккаунта — допустимо по F-06)
- Фильтрация только по owner_id; фильтрация по другим полям (stage, date range) — вне MVP
- Сделки внутри каждой колонки сортируются по created_at DESC (новые сделки сверху) — аналогично всем другим спискам в системе
- Только backend API; фронтенд (drag-and-drop) — задача F-11
- Изменение стадии меняет только поле stage; остальные поля сделки не затрагиваются
- bdm может менять stage любой сделки (не только своей) — нет record-level restriction
