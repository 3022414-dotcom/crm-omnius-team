# Feature Specification: Фронтенд CRM

**Feature Branch**: `011-crm-frontend`

**Created**: 2026-07-05

**Status**: Draft

**Input**: User description: "F-11 UI/UX общий — фронтенд CRM на основе всех реализованных backend API (F-04–F-10). Включает: список аккаунтов, контактов, сделок с фильтрацией и поиском; детальные страницы с заметками, вложениями, активностями; Kanban-доска сделок; авторизация через Google SSO; навигация между разделами. ## Clarifications

### Session 2026-07-05

- Q: Какой фреймворк для фронтенда использовать — Next.js (App Router, SSR) или React+Vite (SPA)? → A: React + Vite (SPA)
- Q: Активности в навигации — убрать или добавить глобальную страницу? → A: Глобальная страница активностей — список всех активностей текущего пользователя с фильтром по статусу и типу
- Q: Форма создания/редактирования — модал или отдельная страница? → A: Модальные окна (modal dialog) — создание и редактирование открываются поверх текущей страницы
- Q: Глобальная страница «Активности» — чьи задачи видны? → A: Admin видит все активности команды + фильтр по пользователю; bdm/viewer — только свои
- Q: Заметки — модал или inline (speckit-analyze F1)? → A: Inline-textarea, исключены из FR-011; ConfirmDialog перед удалением заметки обязателен (SC-005)

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Авторизация и защита маршрутов (Priority: P1)

Неавторизованный пользователь открывает CRM и видит страницу входа с кнопкой "Войти через Google". После успешного входа он попадает на главный экран приложения. При повторном открытии вкладки (если сессия жива) — остаётся авторизованным. При утере сессии во время работы — автоматически перенаправляется на страницу входа.

**Why this priority**: Без авторизации всё приложение недоступно. Это фундамент P1.

**Independent Test**: Открыть CRM без сессии → видна страница входа; нажать Google → пройти OAuth → попасть в приложение; обновить страницу → оставаться авторизованным; принудительно сбросить сессию → при следующем запросе → редирект на логин.

**Acceptance Scenarios**:

1. **Given** неавторизованный пользователь, **When** открывает любой URL CRM, **Then** происходит редирект на страницу входа
2. **Given** страница входа, **When** пользователь нажимает "Войти через Google", **Then** открывается Google OAuth; после успешного входа — редирект в CRM
3. **Given** аккаунт Google не добавлен администратором, **When** пользователь завершает OAuth, **Then** отображается страница с сообщением "Доступ запрещён. Обратитесь к администратору."
4. **Given** авторизованный пользователь, **When** нажимает "Выйти", **Then** сессия завершается, редирект на страницу входа
5. **Given** сессия истекла во время работы, **When** пользователь выполняет любое действие, **Then** происходит редирект на страницу входа без потери данных формы

---

### User Story 2 — Оболочка приложения и навигация (Priority: P1)

Авторизованный пользователь видит постоянную боковую навигацию с разделами CRM и может переходить между ними. На мобильном устройстве навигация сворачивается в бургер-меню.

**Why this priority**: Без оболочки и навигации другие разделы недоступны. P1 вместе с авторизацией.

**Independent Test**: После входа видна боковая панель с пунктами Аккаунты / Контакты / Сделки / Kanban / Активности; клик по каждому открывает соответствующую страницу; на ширине < 768px панель скрывается, появляется бургер-кнопка.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** смотрит на интерфейс, **Then** видит боковую панель с разделами: Аккаунты, Контакты, Сделки, Kanban, Активности; текущий раздел выделен; клик по «Активности» открывает глобальную страницу активностей
2. **Given** любая страница CRM, **When** ширина экрана < 768px, **Then** боковая панель скрывается; появляется кнопка бургер-меню; нажатие открывает/закрывает навигацию
3. **Given** авторизованный пользователь, **When** видит в шапке имя пользователя и аватар (из Google), **Then** может нажать и выйти из аккаунта
4. **Given** операция завершилась с ошибкой (403/404/500), **When** пользователь инициировал действие, **Then** отображается понятное сообщение об ошибке (не сырой JSON/не пустой экран)

---

### User Story 3 — Аккаунты: список и детальная страница (Priority: P1)

Пользователь просматривает список компаний с поиском, открывает детальную страницу аккаунта и видит всю связанную информацию (контакты, сделки, заметки, вложения, активности). Admin/bdm могут создавать, редактировать и (admin) удалять аккаунты.

**Why this priority**: Аккаунты — верхний уровень иерархии CRM. Центральный раздел.

**Independent Test**: `/accounts` → список аккаунтов с поиском; клик → детальная страница с вкладками; создать аккаунт → появляется в списке; отредактировать → изменения сохранены; admin удаляет → после подтверждения аккаунт исчезает.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** открывает раздел Аккаунты, **Then** видит список компаний с пагинацией; каждая строка содержит: название, отрасль, владелец, дату создания
2. **Given** список аккаунтов, **When** пользователь вводит текст в поиск, **Then** список фильтруется по названию в реальном времени (или по нажатию Enter)
3. **Given** список аккаунтов, **When** пользователь с ролью admin/bdm нажимает "Создать аккаунт", **Then** открывается модальное окно с формой; после заполнения и сохранения — модал закрывается, аккаунт появляется в списке без перезагрузки страницы
4. **Given** детальная страница аккаунта, **When** пользователь открывает её, **Then** видит: основная информация + вкладки "Контакты", "Сделки", "Заметки", "Вложения", "Активности"
5. **Given** детальная страница аккаунта, **When** admin нажимает "Удалить", **Then** появляется диалог подтверждения с предупреждением о каскадном удалении; после подтверждения — аккаунт удалён, редирект в список

---

### User Story 4 — Контакты: список и детальная страница (Priority: P1)

Пользователь просматривает список контактных лиц с поиском, открывает детальную страницу. Admin/bdm могут создавать контакты, загружать фото.

**Why this priority**: Контакты — второй ключевой объект CRM, тесно связанный с аккаунтами и сделками.

**Independent Test**: `/contacts` → список; поиск по имени/email; клик → детальная страница с фото (или заглушкой); загрузить фото → отображается; создать контакт → появляется в списке.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** открывает раздел Контакты, **Then** видит список контактов: имя, должность, email, привязанный аккаунт
2. **Given** список контактов, **When** вводит текст в поиск, **Then** фильтрация по имени, фамилии, email
3. **Given** детальная страница контакта, **When** открывает её, **Then** видит: фото (или аватар-заглушку), основные данные, аккаунт, вкладки "Заметки" / "Вложения" / "Активности"
4. **Given** admin/bdm на детальной странице контакта, **When** загружает файл изображения как фото, **Then** фото обновляется на странице
5. **Given** admin на детальной странице, **When** нажимает "Удалить", **Then** диалог подтверждения → после удаления редирект в список

---

### User Story 5 — Сделки: список, детальная страница, связанные контакты (Priority: P1)

Пользователь просматривает список сделок с фильтрацией по стадии, аккаунту, владельцу. Открывает детальную страницу, где видит все связанные данные.

**Why this priority**: Сделки — основной объект воронки продаж. P1.

**Independent Test**: `/deals` → список с фильтром по stage; клик → детальная страница с контактами, заметками, вложениями, активностями; создать сделку → появляется в списке.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** открывает раздел Сделки, **Then** видит список сделок: название, сумма, стадия, аккаунт, владелец, дата закрытия
2. **Given** список сделок, **When** применяет фильтр по стадии, **Then** список обновляется; можно комбинировать с фильтром по аккаунту и владельцу
3. **Given** детальная страница сделки, **When** пользователь открывает её, **Then** видит: основная информация + связанные контакты + вкладки "Заметки" / "Вложения" / "Активности"
4. **Given** admin/bdm на детальной странице, **When** меняет стадию сделки через выпадающий список, **Then** стадия обновляется без перезагрузки страницы
5. **Given** admin/bdm, **When** привязывает/отвязывает контакт к сделке, **Then** список контактов на странице обновляется

---

### User Story 6 — Kanban-доска (Priority: P2)

Пользователь видит сделки в виде Kanban-доски, сгруппированные по стадиям. Admin/bdm могут перетаскивать карточки между колонками для смены стадии. Доска фильтруется по владельцу.

**Why this priority**: Ключевой инструмент управления воронкой, но можно управлять сделками и через список (P5). P2.

**Independent Test**: `/kanban` → 6 колонок; карточки с названием, суммой, аккаунтом, владельцем; перетащить карточку → stage меняется; фильтр по owner → только его сделки.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** открывает Kanban, **Then** видит 6 колонок (lead/qualified/proposal/negotiation/won/lost); каждая карточка содержит: название, сумму, аккаунт, владельца, количество контактов
2. **Given** admin/bdm на Kanban, **When** перетаскивает карточку в другую колонку, **Then** стадия сделки обновляется через API; карточка остаётся в новой колонке
3. **Given** Kanban с фильтром по владельцу, **When** пользователь выбирает конкретного менеджера, **Then** отображаются только его сделки во всех колонках
4. **Given** пустая колонка, **When** пользователь смотрит на доску, **Then** колонка присутствует и отображает "Нет сделок" (не исчезает)
5. **Given** viewer на Kanban, **When** пытается перетащить карточку, **Then** перемещение недоступно (карточки read-only)

---

### User Story 7 — Заметки, Вложения, Активности в контексте сущности (Priority: P2)

Пользователь работает с заметками, файлами и активностями прямо на детальной странице аккаунта, контакта или сделки. Не переходя в отдельный раздел.

**Why this priority**: Контекстная работа — критична для продуктивности. P2, так как основные объекты (US3–US5) нужны сначала.

**Independent Test**: На детальной странице аккаунта → вкладка "Заметки" → добавить заметку → отображается в списке; вкладка "Вложения" → загрузить файл → скачать → удалить; вкладка "Активности" → создать задачу → отметить выполненной.

**Acceptance Scenarios**:

1. **Given** вкладка "Заметки" на детальной странице, **When** admin/bdm пишет заметку и сохраняет, **Then** заметка появляется в списке с именем автора и датой; можно редактировать и (admin) удалять
2. **Given** вкладка "Вложения", **When** admin/bdm загружает файл, **Then** файл появляется в списке с названием, размером; кнопка скачать работает; admin может удалить
3. **Given** вкладка "Активности", **When** пользователь создаёт активность (тип: call/email/meeting/task) с due_date, **Then** активность появляется в списке; просроченные (overdue) выделяются визуально
4. **Given** список активностей, **When** пользователь фильтрует по статусу (выполнено/не выполнено), **Then** список обновляется
5. **Given** активность с completed=false, **When** пользователь нажимает "Отметить выполненной", **Then** статус меняется без перезагрузки страницы

---

### User Story 8 — UX-полировка (Priority: P3)

Интерфейс сообщает о статусе операций: лоадеры при загрузке данных, тосты при успешных/ошибочных действиях, диалоги подтверждения перед удалением.

**Why this priority**: Улучшает UX, но не блокирует основную функциональность. P3.

**Independent Test**: Долгая загрузка → виден скелетон/спиннер; удаление → диалог подтверждения; успешное сохранение → toast-уведомление; ошибка 403 → понятное сообщение.

**Acceptance Scenarios**:

1. **Given** любой запрос к API, **When** данные загружаются, **Then** отображается индикатор загрузки (скелетон или спиннер)
2. **Given** пользователь выполнил успешное действие (создал/обновил/загрузил), **When** операция завершена, **Then** появляется кратковременное уведомление об успехе
3. **Given** любая операция удаления, **When** пользователь нажимает "Удалить", **Then** перед выполнением открывается диалог подтверждения
4. **Given** ошибка сервера (500), **When** пользователь видит результат, **Then** отображается понятное сообщение "Что-то пошло не так. Попробуйте позже." — без технических деталей

---

### Edge Cases

- Список с нулевым количеством записей → пустое состояние с призывом создать первую запись
- Форма создания с незаполненными обязательными полями → инлайн-валидация до отправки
- Файл > 50 MB при загрузке вложения → ошибка до отправки на сервер (клиентская валидация)
- Изображение > 5 MB при загрузке фото контакта → ошибка до отправки
- Потеря сессии при открытой форме → сохранить черновик в localStorage, после входа предложить восстановить
- Viewer пытается создать/редактировать через UI → кнопки скрыты или задизейблены для viewer

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА предоставлять страницу входа с Google OAuth и защищать все маршруты — неавторизованные пользователи перенаправляются на страницу входа
- **FR-002**: Система ДОЛЖНА отображать постоянную боковую навигацию с разделами: Аккаунты, Контакты, Сделки, Kanban, Активности; на экранах < 768px навигация сворачивается
- **FR-003**: Система ДОЛЖНА предоставлять страницу списка аккаунтов с поиском, пагинацией, созданием/редактированием/удалением (по ролям); детальную страницу аккаунта с вкладками: Контакты, Сделки, Заметки, Вложения, Активности
- **FR-004**: Система ДОЛЖНА предоставлять страницу списка контактов с поиском; детальную страницу с фото (загрузка/удаление) и вкладками: Заметки, Вложения, Активности
- **FR-005**: Система ДОЛЖНА предоставлять страницу списка сделок с фильтрами по стадии/аккаунту/владельцу; детальную страницу со связанными контактами, изменением стадии, вкладками: Заметки, Вложения, Активности
- **FR-006**: Система ДОЛЖНА предоставлять Kanban-доску с 6 колонками, карточками сделок и перетаскиванием для смены стадии (admin/bdm); фильтром по владельцу
- **FR-007**: На каждой детальной странице ДОЛЖНЫ работать вкладки "Заметки", "Вложения", "Активности" с полным CRUD в рамках прав пользователя
- **FR-008**: Система ДОЛЖНА отображать визуальные индикаторы загрузки, toast-уведомления о результатах операций и диалоги подтверждения перед удалением
- **FR-009**: Система ДОЛЖНА скрывать или блокировать элементы управления (кнопки создания, редактирования, удаления), недоступные по роли текущего пользователя
- **FR-010**: Система ДОЛЖНА поддерживать светлую и тёмную тему; переключение через кнопку в шапке; при первом посещении применяется системное предпочтение (`prefers-color-scheme`); выбор сохраняется между сессиями
- **FR-011**: Формы создания и редактирования объектов (аккаунты, контакты, сделки, активности) ДОЛЖНЫ открываться как модальные окна поверх текущей страницы; закрытие модала возвращает пользователя в исходный контекст. Исключение: заметки — используется inline-редактирование (textarea в вкладке) как стандартная UX-практика для коротких текстов
- **FR-012**: Система ДОЛЖНА предоставлять глобальную страницу «Активности»: admin видит все активности команды с фильтром по пользователю; bdm/viewer видят только свои; фильтры по статусу (выполнено/не выполнено) и типу (call/email/meeting/task); просроченные активности выделены визуально

### Key Entities

- **Страница входа**: единственная страница, доступная без авторизации; содержит кнопку Google OAuth
- **Application Shell**: постоянная оболочка с навигацией, доступная всем авторизованным пользователям
- **Страница списка**: табличное/карточное представление объектов с поиском, фильтрами, пагинацией
- **Детальная страница**: полная информация об объекте + вкладки с связанными данными
- **Kanban-доска**: визуальное представление сделок по стадиям с drag-and-drop
- **Вкладки сущности**: Заметки / Вложения / Активности — переиспользуемые компоненты на детальных страницах

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% маршрутов CRM перенаправляют неавторизованного пользователя на страницу входа
- **SC-002**: Навигация между разделами работает без полной перезагрузки страницы (SPA-поведение)
- **SC-003**: Все CRUD-операции, доступные через API (F-04–F-10), доступны через UI по соответствующим ролям
- **SC-004**: Кнопки создания/редактирования/удаления не отображаются для ролей, у которых нет соответствующих прав — 0 видимых кнопок-нарушителей
- **SC-005**: Каждая операция удаления защищена диалогом подтверждения — 0 случаев удаления без подтверждения
- **SC-006**: На экранах шириной < 768px интерфейс полностью используем (нет горизонтального скролла в основном контенте)
- **SC-007**: Kanban drag-and-drop обновляет стадию сделки в базе данных — изменение сохраняется после перезагрузки страницы
- **SC-008**: Переключение между светлой и тёмной темой работает без перезагрузки страницы; выбранная тема сохраняется при следующем открытии приложения

### Брендинг

- **Логотип**: `https://omnius.team/logo-omnius.png` — используется в шапке/боковой панели навигации
- **Акцентный цвет**: `#e0503f` (красно-оранжевый) — кнопки действий, активные пункты навигации, ссылки, highlights
- **Тема**: светлая и тёмная (light/dark mode); переключение через кнопку в шапке; предпочтение системы учитывается по умолчанию (`prefers-color-scheme`)

### Типографика и стиль

- Шрифт: системный стек (sans-serif) — отдельный брендовый шрифт не установлен; уточнить при реализации
- UI: минималистичный, без декоративных элементов; плотность данных важнее визуальной сложности

### Применение акцента

- Primary-кнопки (Создать, Сохранить) — `#e0503f`
- Активный пункт навигации — подсветка или левая граница `#e0503f`
- Ссылки и интерактивные элементы — `#e0503f`
- Деструктивные кнопки (Удалить) — стандартный красный (`#dc2626`), не акцент

## Assumptions

- Фреймворк: **React + Vite** (SPA); SSR не требуется для закрытого внутреннего инструмента
- Фронтенд запрашивает API бэкенда по тому же origin (прокси через конфиг dev-сервера) или через env-переменную для API_URL
- Drag-and-drop на Kanban реализуется через lightweight библиотеку (например, @dnd-kit/core) — без jQuery UI
- Состояние: React Context или Zustand (не Redux); серверный стейт — React Query или SWR
- Компонентная библиотека: на усмотрение команды (shadcn/ui, Tailwind CSS — предпочтение простым решениям)
- Раздел «Активности» имеет глобальную страницу (список активностей текущего пользователя) и вкладки на детальных страницах сущностей — оба режима работают параллельно
- При потере сессии — редирект на логин; черновики форм сохраняются в localStorage
- Фото контакта: клиентская валидация размера (< 5 MB) и типа (image/*) до отправки
- Вложения: клиентская валидация размера (< 50 MB) до отправки
